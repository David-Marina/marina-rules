# E-0001 — precomputed pct-change columns go stale

**Symptom.** A `pctChg` (or `pct_chg`, `change_pct`) column disagrees with `close / preclose − 1` in
the same row. In the maintainers' re-adjusted bars, 165,319 of 8,867,227 rows (1.86%) differ by more
than 1 percentage point; counting limit-up days from the column instead of the prices gives 158,668
vs 147,704 (**+7.4%**). Sample: `sh.600000` 2019-02-25, column +11.82%, prices +8.26%.

**Cause (this instance).** The column was *copied through* a price re-adjustment step in the
maintainers' own pipeline: prices were recomputed under a new adjustment, the column was not. The
vendor's original file agreed with its own prices (1 mismatching row in 8.9M, an index). The lesson is
not "vendor X is wrong"; it is that a derived column has no way to know the prices next to it changed.

**Detector.** `python errata/E-0001/reproduce.py <bars_dir_or_csv>` — exit 1 if any row disagrees by
more than `--tol-pp` (default 1.0).

**What to do.** Never read the column. Recompute from `close` and `preclose` at the point of use. If
you must keep the column, regenerate it in the same step that touches prices, and assert equality in CI.

**Consequence if ignored.** Every count of limit-up / limit-down days, "connected boards", sentiment
breadth, or band-violation audit is inflated or shifted. Backtests that gate on "hit the limit" trade
on days that did not.

Sample: [`E-0001/sh.600000_2019-02.csv`](E-0001/sh.600000_2019-02.csv) (7 rows, maintainers' re-adjusted series).
